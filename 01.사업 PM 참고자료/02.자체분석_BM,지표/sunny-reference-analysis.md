## 1. 12강 데이터테이블 만들기 — 핵심 내용

### 1-1. 데이터 테이블의 정의와 목적

- 데이터 테이블 = "게임의 수치를 표로 표현한 것"이며, 일반적인 표 형식에서 **프로그래머가 읽을 수 있는 데이터 테이블 형식으로 변환**해 주어야 한다 (p4).
- 최종 목적은 "서버 프로그래머가 해당 데이터를 무리 없이 읽어들일 수 있게" 하는 것 (p34).

### 1-2. 테이블 설계 순서 (강의가 제시하는 절차)

1. **데이터 수집**: 게임 데이터를 구할 수 있는 사이트(구글 영어 위키, 나무위키, 헝그리앱 등)를 먼저 검색하고, 없으면 직접 플레이하며 수기로 기록한다. 예시: Hay Day fandom 위키 (p5).
2. **속성 → 컬럼 추출**: 레퍼런스의 개체 속성(밀: 오픈레벨 1, 골드 1~3, 생산 시간 2분, 경험치 1, 심는 곳)을 그대로 컬럼으로 정의한다. "이 속성들을 데이터 테이블의 컬럼이라고 한다" (p6~8).
3. **한글 컬럼으로 1차 표 작성**: 번호·이름·오픈레벨·획득 경험치·제작시간 식으로 표를 만든다 (p9).
4. **영문 컬럼명 부여**: 프로그래머가 가져다 쓸 때는 영문이 필요하므로 영문 이름을 지어준다. "구분만 하면 되서 구글번역기 써도 된다" (p10).
5. **데이터 타입 지정**: 정수 int, 소수점 float, 문자 string, 참거짓 boolean. 기획자 확인용 컬럼은 실제 쓰이는 값이 아니므로 **"design" 컬럼**이라고 입력한다 (p11).
6. **최종 납품 형태**: 컬럼명 행 + 타입 행 + 데이터 행 구조로 완성하고, **최초에 작성했던 한글 컬럼명 행은 삭제**한다 (p17, p33~34).

### 1-3. 정규화 규칙 — As-is / To-Be (강의의 핵심 교정 사례)

- **As-is (하지 마세요)**: "태생 별등급 × 현재 별등급" 같은 2차원 매트릭스형 표 — 최대 레벨 표와 필요 경험치 표를 사람이 보는 격자로 작성 (p12), 별등급 × 레벨 1~60의 광폭 매트릭스 (p14).
- **To-Be (이렇게 작성하세요)**: 매트릭스를 풀어 **행 단위(long format)** 로 전환 — `태생별등급 | 별등급 | 최고레벨 | 필요경험치` 4컬럼 행 나열 (p13), `LV | 1성 | 2성 | 3성 | 4성` 형태의 세로 전개 (p15).
- 같은 원리로, 캐릭터가 수백 명이면 위키처럼 캐릭터당 1페이지가 아니라 **여러 개체를 1개 테이블에 행으로** 넣는다. "행에는 캐릭터 네이밍, 우측에는 속성" (p19~21).

### 1-4. 컬럼 규약·문서화 규칙

- **컬럼 사전(3종 세트) 필수**: "수치표만 만들지 말고, 한글칼럼명, 영문 칼럼명, 칼럼설명을 꼭 정리해 주세요. 문서 정리에 꼭 필요합니다. (인수인계에도 필수)" (p16, p31 재강조).
- 컬럼 사전 예시 13컬럼: Index(유닛 고유 코드 1001~1999), **WordIndex(다국어 키 코드 값)**, UnitName, Level, HitPoint, Damage, SensoryRange, AttackRange, TargetUnit/TargetBuilding(boolean, True/False 의미까지 설명), AttackSpeed, Movespeed, MoveType(Ground/Air 열거값 설명) (p16).
- **데이터 타입 사전**: int(정수), float(3.14 등 소수점), string(캐릭터 제목·설명 등 UI에 노출되는 한글), Bool/Boolean(1/0, TRUE/FALSE), list&lt;int&gt;·list&lt;float&gt;(자주 변하지 않는 여러 값을 한 번에) (p32).
- **List 타입 활용**: 한 컬럼에 여러 값을 넣을 때 List형 사용. 예: Rewardtype1=`3,4,10,7` + Rewardvalue1=`100,3,2,132` = "3번 아이템 100개, 4번 아이템 3개…". "주로 퀘스트에서 칼럼 수를 줄이는 목적으로 사용" (p18).

### 1-5. 시트 구성 — 시스템을 이루는 테이블 세트의 예

- **공식 + 참조 테이블 분리**: 가상 전투 공식(기본 대미지 → 속성 상성 ±20% → 구슬 개수 계수 → 치명타 2배, 계산 순서 (1)→(2)→(3)→(4) 명시)을 정의하고 (p22~23), 이를 뒷받침하는 **속성 상성표**와 **구슬 개수별 계수표**를 별도 표로 만든다 (p24).
- **스테이지 테이블**: 번호·지역·던전·스테이지·속성·에너지 소비·배틀횟수·경험치 (p25).
- **강화 합성 시스템의 4테이블**: ① 등급별 다음 레벨업 필요 경험치("기름통의 크기") ② 등급별 되팔기 가격 (p27~28) ③ 등급별 재료로 사용 시 오르는 경험치("들어가는 기름의 양") ④ 강화 합성 시 필요 게임머니 (p27, p29).
- **계정(전체) 레벨 테이블**: 레벨별 필요 경험치 + 레벨업에 따라 바뀌는 수치(에너지·최대 코스트·친구 수)를 표로 표현 (p30).

### 1-6. 실무 팁 요약

- 수백 페이지 분량을 엑셀 낱장으로 쓰는 것은 "매우 끔찍" — 반드시 테이블화 (p19).
- 실데이터를 채운 완성 예시(바바리안/아처 각 10레벨 행)를 만들어 검증한다 (p17, p33~34).
- 다국어 텍스트는 직접 넣지 않고 WordIndex(키 코드)로 참조한다 (p16).

## 3. 14강 스펙리스트와 사운드 기획 — 핵심 내용

### 3-1. 스펙과 버전의 개념

- SPEC(Specification) = 자세한 설명서·사양. "모든 기획서가 준비가 끝났다면, 실제 구현을 위해서는 **버전 스펙을 잡고** 진행을 해야" 한다 (p4).
- 버전 단계: PC 온라인(3~5년 개발) 시절엔 프로토타입–알파–클로즈베타–오픈베타–상용화 5단계였으나, 모바일(6~12개월)은 **프로토타입–알파–오픈베타/상용화 3단계로 간략화**하는 추세 (p5).

### 3-2. 버전 단계별 스펙 기준 (가상 MORPG 예시)

- **프로토타입**: 목적 = 핵심 재미 구현 체크 + 알파 진행 가/부 결정. 최소 스펙 예시: 캐릭터 2, 몬스터 2, 전투 애니메이션 각 2, 스킬 애니메이션 각 1, 타격/죽음/클리어/실패, 기본 GUI (p6).
- **알파**: 목적 = 핵심 재미 + 전체 시스템 완성 체크(양적인 부분 제외, **핵심 시스템의 뼈대 완성**), 기본 상용화 시스템 완성, FGI로 유저 의견 수렴 (p7). 스펙은 **전 항목 수량 명시**: 캐릭터 5종·몬스터 5종·코스튬 10종·무기 6종·스킬 5종, 재화 3종, "30분 이상의 물리적 플레이 타임 보장(PVP 10분, PVE 20분)", UI 시스템(장착/강화/합성), 웹 서버 저장 기능 (p8).
- **오픈베타/상용화**: 콘텐츠 양 확장(PVE 스테이지 100종, 몬스터 80종, 무기 50종 등) + 밸런스 완성 (p9). 기타 시스템 10종(튜토리얼·도움말·퀘스트·상점·착용 레벨 제한·아이템 조합·메신저 등)과 함께 **서버 유저 로그·운영툴(게임 통계/운영 통계), QA 기준(1급 버그=서버 크래시, 2급=기능 미구현/오동작 각 0개), 네트워크(동접 2만, 클라 40MB 이하), 보안(클라 암호화·어뷰징 정책)** 까지 스펙에 포함 (p10).

### 3-3. 체크리스트와 인력 계획

- **체크리스트**: 개발 도중 진행률을 실시간 파악하기 위한 문서. **Step1/Step2/Step3 트리 구조**(예: 로딩화면 > 로딩바 > …)로 기능을 분해하고, 각 말단 항목에 **디자인 소스 / 개발 적용 / 수정사항** O 표기 + 수정사항 설명을 기록 — "어떤 리소스가 얼마나 나와 있는지, 기획·개발·그래픽의 진행 수준을 전체적으로" 파악 (p11).
- **필요 인력 계획**: 인력=예산 문제. 샘플 3종 모두 **개발 스펙 / 디자인 스펙을 분리 서술**하고 예상 개발 기간과 예상 최소 인원을 산출 — 퍼즐 4~5개월·4명 (p12), 턴제 MORPG 8~10개월·7명 (p13), SNG 6~8개월·8명 (p14). 2D보다 3D, 캐주얼보다 RPG가 리소스·인력이 더 필요 (p12).

### 3-4. 사운드 기획

- **BGM**: 1가지가 아니라 로딩 화면·진입 화면·플레이 화면·이벤트 스테이지·레이드 스테이지 등 **화면/모드별로 분류해서 몇 가지로 나눈다** (p16).
- **SFX**: ① 각 UI 버튼을 터치할 때의 효과음 ② 게임 플레이 효과음 — 공격, 스킬, 이펙트, 보상 획득, 스테이지 클리어, 레벨업 등 ③ **시스템 이벤트 효과음 — 합성/진화 시스템이 있다면 합성할 때·진화할 때 나오는 소리, 가챠 시스템이 있다면 가챠를 돌릴 때 나오는 효과음** (p17). 즉 게임에 존재하는 시스템마다 그 이벤트의 소리를 전수 설정해야 한다.

## 5. 반영 우선순위 Top 3

### 1위 — 각인 이벤트별 SFX 스펙 표 신설 (14강 p17 근거)

- **무엇을**: "분해/각인 SFX" 한 줄을 이벤트 단위로 분해한 SFX 스펙 표. 최소 7행 — ① 각인 시도(버튼) ② 실패 + 기운 축적 게이지 상승(**처벌형 금지 원칙에 따라 부정음이 아닌 축적/저금 톤** — plan §3-3 연동) ③ 천장 도달 예고(스택 4, 100% 표기 시) ④ 성공 판정 ⑤ 신·구 비교 팝업 등장 ⑥ "적용" 확정(각인 VFX 동반) ⑦ "유지" 선택. 계열 지정 탭 전환음은 공통 UI 정책 참조로 처리.
- **어디에**: v4 HTML §16(마진법 각인) UI 페이지의 연출 블록 + 문서 관리 페이지의 읽기 가이드 SOUND 행 갱신. plan-final-v2 §9 UI 요구사항 표에 "SFX" 열 추가.
- **왜**: 14강은 합성·가챠처럼 시스템 고유 이벤트마다 소리를 전수 설정하라고 요구한다(p17). 각인은 확률 시도(가챠)+장비 성장(합성)의 복합 이벤트인데 현재 SOUND 스펙이 1단어라 사운드 발주가 불가능한 수준이며, "실패=비처벌 톤"이라는 기획 의도가 사운드 부서에 전달되지 않는다.

### 2위 — 신설 engrave 3테이블 컬럼 스펙 + 다국어 키 컬럼 (12강 p16·p31 근거)

- **무엇을**: `engrave_master` / `accessory_engrave` / `engrave_cost_master`에 accessory_master(§12.2)와 동일 양식의 **컬럼/타입/제약/설명 표** 추가. 이때 `engrave_master`에 **`name_key`·`desc_key`(string)** 컬럼을 신설해 효과명·조건 텍스트를 다국어 키 참조로 전환(12강 WordIndex 패턴, p16). `engrave_cost_master`는 stack 0~4 실데이터 예시 행(60→100%)을 함께 노출.
- **어디에**: v4 HTML §16 데이터 테이블 페이지(현재 ERD 요약만 있는 곳)에 컬럼 스펙 표 추가, §12 네이밍 규칙에 `_key` 접미 규약 1행 추가. plan-final-v2 §7 스키마 블록 갱신.
- **왜**: 12강은 "수치표만 만들지 말고 컬럼명·설명을 꼭 정리하라(인수인계 필수)"를 두 번 강조한다(p16, p31). 이번 개정의 핵심 신설물인 3테이블만 컬럼 스펙 상세가 빠져 있어, 기존 테이블 대비 문서화 수준이 역전된 상태다.

### 3위 — P0/P1/P2 ↔ 버전 게이트 매핑 + 각인 파생 체크리스트 (14강 p5~11 근거)

- **무엇을**: plan-final-v2 §1-3 우선순위 표에 "구현 버전" 열 추가 — P0=알파(핵심 시스템 뼈대: 시도/천장/효과 풀/선택 교체/스키마), P1=오픈베타(계열 지정/잠금/주간 확정 개편/UI 노출), P2=라이브(희귀 등급/연출 확장/무료 각인). 여기에 14강 p11 양식의 Step1(각인)>Step2(기능)>Step3(리소스) 체크리스트를 파생해 소스/적용/수정 진행을 추적.
- **어디에**: plan-final-v2 §1-3 확장 + 작업 폴더(`00.기획/04.장신구-장착-강화/`)에 체크리스트 시트 1건. v4 HTML은 문서 관리 페이지의 파이프라인 표에 버전 열만 반영.
- **왜**: 14강의 핵심 주장은 "기획서가 끝났으면 버전 스펙을 잡아야 구현이 시작된다"(p4)이다. v4는 기능 우선순위(P0~P2)까지는 있으나 그것이 어느 마일스톤의 완성 조건인지가 없어, 알파 시점에 "핵심 시스템의 뼈대 완성"(p7)을 판정할 기준이 문서상 부재하다. Tech Stack 결정 후 구현 착수 시 바로 필요해지는 층이다.

## 1. 16강 밸런스 기획 개념 — 핵심 내용

### 1-1. 밸런스 기획의 정의와 수단 (p4~5)

- 캐릭터·몬스터·장비는 그래픽으로 보이지만 실체는 **여러 수치 요소의 집합**이며, 이 수치가 전투·강화·스테이지·PVP 등 게임 전반과 재미에 막강한 영향을 준다 (p4).
- 밸런스 기획 = "재미에 큰 영향을 주는 수치들을, 플레이어가 재미를 느끼면서 **게임 월드가 붕괴되지 않도록** 균형 있게 설정·조정하는 파트" (p5).
- 수단은 수치·수식 조정만이 아니다 — **게임 규칙이나 각 요소의 규칙을 조정해서 밸런스를 잡기도 한다** (p5). (수치 조정과 규칙 조정의 이원 수단)

### 1-2. 밸런스 3유형 (p6~7)

| 유형 | 내용 | 강의 예시 |
|------|------|----------|
| 유저 ↔ 유저 | 유저 간 공평한 경쟁 | 엘로레이팅 매칭, 과금 유저의 성장 속도 우위 설계 (p6) |
| 시스템 ↔ 유저 | 진행도 대비 보상·성장 속도 | 성장이 너무 빠르면 콘텐츠 소비 과속, 너무 느리면 루즈 — 적절한 속도·보상 조절 (p6) |
| 시스템 ↔ 시스템 | 요소 간 균형 (직업 간, 콘텐츠 간) | 균형이 깨지면 **플레이어가 사용하지 않는·필요로 하지 않는 요소**가 생김 → 모든 요소가 유효가치를 갖도록 조정 (p7) |

### 1-3. 밸런스와 게임 수명 — 초기 설정의 중요성 (p5, p8)

- 수치 하나가 잘못 들어가면: 직업 간 균형 붕괴 → 유저 불만 → 직업 쏠림 → 아이템 시세 붕괴 → **게임 월드 자체가 붕괴**하는 연쇄를 강의가 단계별로 예시 (p5).
- "게임 밸런스가 서서히 붕괴됨과 동시에 게임도 끝난다." **밸런스는 수정할수록 망가지게 되어 있으므로, 처음 개발할 때 잘 맞추는 것이 중요** (p8).
- 단, **완벽한 밸런스는 존재하지 않는다** — 등가 밸런스를 목표하기보다 항상 모니터링하며 게임 메타에 맞게 유연하게 조정하고, 최대한 적은 사람이 불만을 갖도록 패치한다 (p8).

### 1-4. 밸런싱 절차 — 기준점 앵커링 방법론 (p9~17) ★ TBD 확정 방법론의 핵심

액션 MORPG 기준 밸런스 작업 순서 (p9~10):

```
[1 STEP] 전투 밸런스 → [2 STEP] 성장 밸런스 → [3 STEP] 보상·경제 밸런스
```

- 1 STEP: 몬스터를 처치하는 **기준** 정하기 → 기준에 맞는 전투 공식 → 콘텐츠에 몬스터 배치 (p9)
- 2 STEP: 레벨업 필요 경험치, 레벨 상승 필요 시간, 상승 능력치 (p9)
- 3 STEP: 스테이지 보상, **레벨업 시간에 맞게 보상 배분**, 각 아이템의 가치 책정 (p9)

기준점을 잡는 구체 절차 (피격 횟수 사례, p12~17):

1. **체감 기준 질문을 먼저 던진다**: "몬스터가 몇 대 맞고 죽어야 재미있는가?" — Case 1대/4대/30대/100대 비교 (p12).
2. **양극단을 배제한다**: 1방 처치는 허무·지루(단, 성장 후 저레벨 던전에서의 1방은 합당) (p13), 30~100대는 일반 몬스터에게 과도한 시간 소모로 지루 (p14).
3. **경쟁작 조사로 보편 구간을 좁힌다**: 다른 액션 RPG를 조사하면 경험적으로 **3~10회가 적당한 피격 횟수** — 몬스터 종류·유저 레벨·능력치에 맞게 조정 (p15).
4. **전투 재미를 최우선 기준으로 고정한다**: 성장·경제·보상이 잘 짜여 있어도 전투가 재미없으면 유저는 떠난다. **전투에서 재미있을 수치 기준을 먼저 잡고 나머지를 그것에 맞춘다** (p16).
5. **일단 기준을 확정하고 시작한다**: "4대가 자연스럽다면 일단 4대를 기준으로 잡는다. 이 기준은 나중에 충분히 바뀔 수 있고 전체를 조율하면서 바꾸면 되므로, **기준을 잡는 것을 두려워하지 말자**" — 이 공격 횟수 4회가 기준이 되어 전투 공식과 여러 밸런스를 맞추기 시작한다 (p17).

> **TBD 확정 방법론 관점 요약**: 16강의 절차는 ① 체감 기준(플레이어가 느끼는 재미) 정의 → ② 극단값 배제 → ③ 레퍼런스 조사로 보편 구간 확보 → ④ 구간 내 단일 기준값 선언 → ⑤ 그 앵커에서 나머지 수치를 역산·전파 → ⑥ 전체 조율 단계에서 앵커 자체도 수정 허용. 즉 "정답을 찾을 때까지 보류"가 아니라 **"근거 있는 임시 기준을 선언하고 체계를 먼저 세우는"** 방식이다.

## 3. 5강 게임 지표(KPI) — 핵심 내용

### 3-1. 사용자 지표 (p4~14)

| 지표 | 정의·공식 | 비고 |
|------|-----------|------|
| PV | 중복 포함 접속 총 횟수 — 서비스 활성도 (p5~6) | |
| UV | 중복 제외 접속자 수 (p7~8) | |
| DAU / WAU / MAU | 일/주/월 단위 중복 제외 순 사용자 — **서비스 이용도의 가장 중요한 지표** (p9) | |
| Retention Rate | 재방문율 = 현재 접속자 ÷ 비교 시점 접속자. D+1 ~ D+7 추적 (p10) | **통상 퍼즐 D+1 60%↑, RPG 등 코어 게임 D+1 50%↑**이어야 유저가 쌓이는 구조. 마케팅 집행 의사결정 척도 (p11) |

### 3-2. 게임 플레이·UA 지표 (p15~20)

- **Session Length**(1회 접속 체류 시간 — 몰입도, p15), **Session Count**(일일 플레이 횟수 — 재방문 습관, p16), **Stickiness = DAU ÷ MAU × 100**(충성도, p17).
- UA: **CAC**(총 마케팅비 ÷ 획득 유저 수, p18), **Virality**(신규 ÷ 기존 유저, p19), **ROI**((수익-마케팅비) ÷ 마케팅비 × 100, p20).

### 3-3. 매출 지표 (p21~36)

| 지표 | 공식 | 근거 |
|------|------|------|
| Revenue / 영업이익 | 매출액 − 판관비 = 영업이익 | p21~22 |
| PU / PU Rate | 결제 유저 수(중복 제외) / PU ÷ DAU | p23~24 |
| ARPU | 일 매출 ÷ DAU | p25~26 |
| ARPPU | 일 매출 ÷ PU | p27~29 |
| LTV | ARPU × (1 ÷ Churn) — 1인당 마케팅비 상한 의사결정에 사용 | p30~32 |

- 플랫폼별 PU 비율: 온라인 게임 MAU의 8~13%, 모바일 4~8%. 예상 월 매출 = PU × ARPPU (p33). 장르별 PU는 RPG가 1위 — 코어할수록 PU가 많다 (p34).
- 헤비 유저 루프: 첫 결제 → PU 전환 → 맘에 드는 상품 발견 → 재결제 반복, **콘텐츠 소진 시 이탈 → 지속 업데이트가 중요** (p35). 라이트 유저는 충성도가 쌓이면 PU로 전환 (p36).

### 3-4. 지표 샘플과 매출 솔루션 사례 (p37~52)

- 샘플: 레벨별 DAU/MAU/가입자 (p37~39), 월간 최대 동접 비교 (p40), 월간 매출 비교 (p41), PU 비교 (p42), 액티브 비교 (p43), 일자별 코호트 리텐션 (p44), 레벨별 객단가·유저 분포 (p45), 플레이타임별 유저 분포 (p46), 레벨별 평균 플레이타임 (p47).
- 분석→솔루션 사례: 레벨대별 구매율 분석 결과 41LV 이상은 구매율 90%+인데 1~40LV은 0.16~30%로 낮음 → **"최초 구매 유도 장치(미끼 상품) 부족"** 진단 (p48~49). 미끼 상품의 기본은 "경험"과 "**모은 것에 대한 아까움**" (p50~51). 매일 로그인 시 게임머니+캐쉬로 여는 보물상자 지급(열쇠 100원, 최소 충전 3,000원, 상자 기대값 300~1,500원) → **6개월 평균 매출 1.8배 상승** 사례 (p52).

### 3-5. 지표 설계 프로세스와 로그 설계 (p53~69) ★ 시스템 기획자의 실무 핵심

1. **기능 리스트에서 로그를 먼저 설계** → 서버 개발자에 전달해 로그 적재 → 분석 항목을 설계해 운영툴 그래프로 구현 (p53, p67~68).
2. **운영툴에는 하루마다 갱신할 중요 데이터만** 남기고, 월 1회 수준의 데이터는 로그로 쌓아 뒀다가 개발자에게 요청해 추출 (개발 리소스 절약) (p54).
3. 로그 구성 4대 중점 (p55~56, p69):
   - A. 시간 흐름에 따른 추적·분석 가능
   - B. **6하 원칙**(누가/언제/어디서/어떻게/무엇을/무엇에게) 기본 구성 (p58에 획득 로그 실례)
   - C. CS(계정 도용·오류로 인한 아이템/재화 소실) **복구의 명확한 근거 자료** 확보
   - D. 버그 악용(아이템·재화 복사, 의도치 않은 취득) **역학 추적** 가능
4. 로그 샘플 형식: 행동 항목 / 행동 내용 / 행동 패턴 경로 / Value(1)~(9) / TIME / Place — 재화 소모 로그는 **소모 전·후 잔량을 함께 기록** (p59~63).
5. 표준 데이터 항목: 동접·매출·액티브·신규·삭제·결제·잔존·상점/가챠 판매 (일·주·월) (p64), **재화별 충전/소진/보유 3종 세트** (p65).
6. 퍼널 분석: 튜토리얼~초반 스테이지 각 지점의 통과율·이탈자 수를 추적해 최다 이탈 지점을 개선 (p66).

### 3-6. MORPG 지표 기획 — 7대 관심 영역과 활용 (p70~89)

| 영역 | 필요 지표 | 활용 (근거) |
|------|----------|------------|

- p90~105는 SNG 장르 사례(생산·가판대·친구 로그와 지표): **장르 특성에 따라 지표 설계가 달라진다**는 원칙 예시 (p90).

## 5. 반영 우선순위 Top 3

### 1위 — 각인 시스템 로그 설계 명세 신설 (5강 p53~69)

지표는 로그에서 시작하는데 v4에는 행동 로그 설계가 전무하다. 특히 각인은 **확률 판정 + 파편 소모 + 적용/유지 선택**이 결합된 트랜잭션이라 CS 분쟁·버그 악용 추적(p56, p69 C·D)의 최우선 대상이다. 6하 원칙 + 소모 전후 잔량 기록(p58, p60) 형식으로 각인 시도/분해/주간 확정 로그 시트를 만들어 §7 스키마 옆에 배치한다. **로그는 출시 후 소급 불가**이므로 구현 전 확정이 필수 — 우선순위 1위의 근거.

### 2위 — 부록 A를 "설계 기대값 ↔ 라이브 검증 지표" 대응표로 확장 (5강 p65·p72·p77 × 16강 p8)

16강은 "밸런스는 상시 모니터링·유연 조정"(p8)을, 5강은 그 수단(경제 밸런스 지표 p77, 성장 콘텐츠 시도 지표 p72)을 제공한다. 부록 A 4지표 각각에 검증 지표·허용 밴드·이탈 시 1차 조정 수단을 붙이고, 특히 **주간 확정 사용률**(2주 vs 25일 민감도의 전제)과 **런당 파편 실측**(4개/런 — 경제 전체의 기점), **실측 성공률·"유지" 선택률**을 핵심 감시 지표로 지정한다.

### 3위 — 전투 체감 앵커 선언으로 TBD 수치 확정 절차 가동 (16강 p9~17)

강의의 밸런스 순서는 전투 → 성장 → 보상·경제인데, v4는 경제(§8)가 가장 정밀하고 전투 앵커가 비어 있다. 피격 횟수 3~10회 방법론(체감 기준 → 극단 배제 → 레퍼런스 구간 → 단일 기준 선언, p12~17)을 적용해 "각인 1개의 전투 체감 목표치"를 먼저 선언하고, 여기서 EG-A1~C4 예시값과 부옵션 롤 값(가드레일의 앵커)을 역산한다. "기준을 잡는 것을 두려워하지 말자"(p17) — TBD를 '검수 대기'가 아닌 '근거 부기된 작업 기준값'으로 승격하는 것이 강의 방법론의 결론이다.

## 1. 2부 3강 시스템기획 vs 콘텐츠기획 — 핵심 내용 (페이지 근거)

### 1-1. 왜 이 구분이 중요한가 (p4~5)

- "시스템 기획과 콘텐츠 기획의 차이"는 기획 지망생이 가장 많이 혼동하는 질문 (p4).
- 이 구분을 모르면 **기획서 범위를 애매하게 잡아** 좋은 포트폴리오를 완성하기 어려움 — 반드시 이해하고 넘어가야 한다 (p5).
- 유저가 말하는 "게임 콘텐츠"와 개발사의 "콘텐츠 기획"은 텍스트만 같고 의미가 전혀 다름 (p6~7).

### 1-2. 시스템 기획의 정의 (p8)

시스템 기획은 **기능적인 것** — 아래 3가지를 정의하는 작업:

1. 게임 규칙과 UI 등이 **동작하는 기능의 정의**
2. 기능 동작에 필요한 **데이터 테이블 구조** 설계, AI 등
3. 여러 **데이터의 타입**(퀘스트, 스킬, 레벨 디자인 구성요소, NPC 표정 등) 설계

### 1-3. 콘텐츠 기획의 정의 (p9)

콘텐츠 기획은 **비기능적이고 양적인 것**:

- 만들어진 퀘스트 타입에 맞춰 **수백 개의 퀘스트를 만드는 것**
- 아바타 게임의 수많은 의상 설정, 캐릭터·몬스터 설정, 퀘스트 대사 입력
- **퀘스트 보상 정하기, 요일 던전·레이드·무한 던전 등에 보상 정해서 입력하기**

### 1-4. 공룡 비유 — 구조 모델 (p10~15)

| 비유 | 대응 개념 | 근거 |
|------|----------|------|
| 공룡 | 게임 | p13 |
| 공룡 뼈대 | 게임 시스템 (머리=전투, 허리뼈=스테이지, 팔=아이템 강화, 다리=능력치·성장, 꼬리=친구/소셜) | p11, p13 |
| 뼈대를 움직이게 하는 것 | 게임 규칙 | p12~13 |
| 전체 공룡의 모양 | 게임 전체 구조 — 시스템·규칙들이 유기적으로 융합 | p12~13 |
| 공룡 피부(SKIN) | UI 기획 — 시스템 기획과 따로가 아닌 **한 몸** | p14~15 |
| 공룡의 살 | 콘텐츠 기획 | p15 |

- 시스템·룰 기획은 "공룡의 뼈대를 세우는 것" — 제대로 하면 **메인 기획을 할 수 있는 것**과 같음 (p10).
- 시스템 기획은 **게임 규칙 기획과 UI 기획을 품고 있다** (p11, p14).

### 1-5. 판별 공식과 부모-자식 관계 (p16~17)

- 판별 공식 (p16): **퀘스트 UI + 퀘스트 규칙 기획 = 퀘스트 시스템 기획**, 퀘스트 리스트를 여러 개 만들어 내는 것 = 콘텐츠 기획.
- 관계 규정 (p17): 콘텐츠가 시스템을 싸고 있는 것이 아니라 **시스템이 부모, 콘텐츠가 자식**. 따라서 **시스템 기획이 먼저 잡혀야** 그에 해당하는 콘텐츠 기획을 할 수 있다.

## 3. 1부 4강 상용화 모델(BM) — 핵심 내용

### 3-1. BM 개념과 모델 종류 (p4~8)

- BM = 게임 개발사와 퍼블리셔가 수익을 창출하는 방식. 장르·대상 사용자·시장 환경에 따라 다르게 적용 (p4).
- 7가지 모델: **B2P 패키지**(초기 수익 높으나 지속 수익 어려움), **F2P 부분 유료화**(아이템·스킨·강화·편의 기능 판매 + 인앱 구매·가챠·광고 — 진입 장벽 낮으나 과도한 과금 유도 시 불만) (p5), **정액제**(안정적 수익, 진입 장벽 높음), **혼합 모델**(다양한 유저층 공략, 과금 구조 복잡화 위험) (p6), **P2E**(시장 변동성·규제 민감), **DLC/확장팩**(생명력 연장) (p7), **게임 패스/클라우드 구독** (p8).
- 모델 선택 고려사항 5가지: 타겟 사용자 층 / 게임 장르 / 시장 트렌드 / 기술 발전 / 경쟁 상황 (p9).

### 3-2. 상용화 모델 분석 프레임 6가지 (p10~17)

1. **사용자 중심 분석** (p11): 페르소나 정의(하드코어=정액제 선호·캐주얼=무료 진입 선호) + 행동 데이터(MAU/DAU, 1·7·30일 잔존율, ARPU, ARPPU — 상위 과금 유저 집중도).
2. **시장·경쟁 환경 분석** (p12): 트렌드, 경쟁 게임의 매출원·성공/실패 요인, 지역별 특성(아시아=F2P·가챠, 북미/유럽=정액제·DLC).
3. **재무·수익성 분석** (p13): 수익원 구성, LTV, CAC vs ARPU 비교(CAC>ARPU=비효율), 매출 80%를 상위 20% 유저(고래)가 차지하면 **과도한 의존으로 좋지 않음**.
4. **콘텐츠-과금 적합성** (p14): **과금 콘텐츠가 유저의 핵심 플레이 경험을 방해하지 않는가**. 경쟁 게임(FPS/MOBA)=스킨·장식, RPG=장비·캐릭터·가챠 선호.
5. **유저 피드백·커뮤니티 반응** (p15): 부정 반응 = "페이 투 윈", "과금 유도 압박" / 긍정 반응 = "공정한 과금", "선택적 과금".
6. **장기 운영·성장 가능성** (p16): 리텐션 요소(주기적 업데이트·이벤트/보상), 확장 가능성(DLC·시즌 패스·글로벌).
- 분석 결과 활용 순서: 모델 선택/조정(초기 부분유료→후기 정액제 추가) → 주요 매출원 집중 홍보 → 유저 불만 누적 방지 (p17).

### 3-3. BM 개선 6원칙 (p28~34)

1. **사용자 중심 개선** (p28): P2W 요소·지나친 과금 유도를 피드백으로 파악, 진입장벽 낮추기(무료 체험).
2. **게임 내 경제 시스템 개선** (p29): **공정성 유지 — 유료 구매가 게임 내 밸런스를 해치지 않도록 설계**(스킨 등 비경쟁 요소 집중) + **무과금 유저도 꾸준히 플레이하면 유료 혜택을 얻을 수 있는 시스템**(플레이 타임 보상, 희귀 아이템 드랍 확률 제공).
3. **과금 모델 다양화** (p30): 혼합 모델 + **가치 기반 과금 — 가챠 시스템에서 "보장 시스템" 도입(일정 횟수 시 원하는 아이템 제공)**.
4. **재방문율 증가** (p31): 정기 이벤트, 시즌 패스(무료/프리미엄 이원화 — Fortnite, Genshin Impact 등).
5. **신규·복귀 유저 유입** (p32): 초보자 패키지, 복귀 캠페인.
6. **유저 신뢰 확보** (p33): **투명성 강화 — 가챠 확률·유료 서비스 제공 조건 명시, 과금 정책 공개** + 강압적 과금 유도 지양, 자연스러운 선택 구조.
- 결론 (p34): **"유저의 즐거움을 해치지 않는 선에서 수익성을 극대화"** — 지속적 데이터 분석과 유저 피드백이 필수.

### 3-4. 매출 지표와 시뮬레이션 (p35~50)

- DAU/MAU(중복 제거 순 이용자) (p35), PU(결제 유저 수)·ARPPU(=월 매출/월 결제 유저) (p36).
- **예상 한달 매출 = PU × ARPPU**. PU는 통상 온라인 게임 MAU의 8~13%, 모바일 MAU의 4~8%. 코어 장르(RPG)일수록 PU 높음. 부분 유료화 구조에 따라 PU가 크게 달라지며 이벤트·업데이트로 상승 가능 (p37).
- 헤비 유저가 먼저 PU 전환, 라이트 유저는 충성도가 생긴 뒤 전환 — PU 상승은 게임에 악영향 없이 매출을 만드는 좋은 방법 (p38).
- **고 객단가**(소수 충성 유저 주력) vs **저 객단가**(박리다매) (p39). 상용화 강도 분석: 저가/고가 비율, **기능성/비기능성 아이템 비율**, **기간제/영구제/소모제 비율**로 경쟁 게임 BM 강도를 정량 비교 (p40~41).
- 매출 시뮬레이션 프로세스: 예상 MAU → 장르별 PU% → ARPPU → 시간에 따른 유저·매출 하락 반영해 연간 매출 산정 (p42~46).
- 유료 상품 설계는 최근 **게임기획자와 사업 PM이 모두 하는 추세** — 경계가 모호해짐 (p47). 판매 지표(평균 결제 금액·리텐션 결제자 비율·잘 팔리는 상품)를 모니터링해 저성과 상품을 개선하고 신상품을 기획 (p48~49). 월 정액 서비스 가격표 제안 예시 (p50).
- 참고: 상용화 콘텐츠 분석 사례 — 레벨별 유저 급감 지점에서 **"사용해야 할 재화보다 획득 재화가 너무 적다"**를 발견 → ① 해당 구간 재화 소모량 축소 ② 초반 구간 재화 획득 패키지 상품 출시로 개선 (p22~23).

## 5. 1부 11강 게임 QA — 핵심 내용

### 5-1. QA 개념·범위·직무 (p4~11)

- QA 흐름: **기획서 기반 TC 작성 → TC 기반 버그 테스트 → 버그 보고 → 버그 수정 후 확인 테스트**. 기획자가 기획서를 쓰면 QA 리더가 기획서 기반으로 TC를 작성. **TC는 유저가 할 수 있는 모든 행동을 항목화한 리스트** (p4).
- QA 범위 3분류 (p5): **기능 테스트**(기능 명세: 캐릭터·스킬·UI·아이템·전투 등 / 사양 / 네트워크), **성능 테스트**(부하 / 보안 프로그램), **Fun QA**(게임성·접근성·플레이 경험 / **밸런스 테스트: 성장 밸런스·경제 밸런스**).
- 직무: ① TC 작성(“특정 아이템 사용 후 캐릭터가 정상 반응하는가” 수준까지, p6) ② 버그 탐지·보고 — 재현 방법을 명확히, 이슈 라이프사이클 OPEN→IN PROGRESS→RESOLVED→CLOSED(리오픈 포함) (p7) ③ 기기 호환성 (p8) ④ Fun QA — 전투/성장/보상·경제 밸런스 (p9) ⑤ LQA (p10) ⑥ **회귀 테스트 — 수정된 버그의 재발 확인 + 신규 기능이 기존 기능에 영향 없는지 확인** (p11).
- 결과 값: Pass / Fail / Impossible(수정 불가) / Not tested. **버그 등급: S급=서버 다운·접속 불가, A급=기능 미구현·잘못 구현, B급=마이너 이슈, C급=안고 가도 되는 버그, Non Issue** (p11, 재정의 p14).

### 5-2. QA 프로세스 (p12~17)

- 빌드 단계별 QA (p12): 개발 빌드=기능·콘텐츠 QA → 고도화/런칭 빌드=+밸런스·호환성·Fun QA·LQA·통합 QA → 라이브=신규 콘텐츠·이벤트 QA·이슈 관리.
- 프로세스 6단계 (p13~15): ① QA 담당자(**없으면 기획자**)가 기획서 기반 TC 작성 ② TC 기반 QA + **TC 기반이 아닌 랜덤 QA도 병행** ③ JIRA 등 BTS에 이슈 업로드(제목·이미지·영상·정상 동작·현재 상태·수정되어야 하는 상태 구분) ④ 담당자 할당 ⑤ 해결 후 보고자에게 재할당 ⑥ 재테스트 후 리오픈 또는 클로징. 버전별 폴더로 이슈 관리.
- 버그 이슈 양식 (p16~17): \[버그 사항\] / \[버그 내용\] / \[수정되어야 할 내용\]의 쌍으로 기술.

### 5-3. QA 원칙과 PDCA (p18~34)

- 목적: 오류 예방으로 품질 보증 — 고객 만족, **비용 절감(오류 예방으로 수정 비용 감소)**, 효율성 (p18). 기본 원칙 4: 고객 중심 / **예방 중심(문제 발생 전 식별·방지가 QA의 핵심)** / 지속적 개선 / 데이터 기반 결정 (p19).
- **PDCA 사이클** (p21): Plan(품질 목표·TC 계획: 산출물=품질 관리 계획서·테스트 계획서, p23~25 — 테스트 시나리오 정의, **경계 테스트: 엣지 케이스·비정상 입력**, 기능 테스트) → Do(개발 QA→통합 QA→사용자 환경 QA, 문서화, p26~30 — 성능/부하/스트레스 테스트, 결함 관리: **Critical=즉시 해결(결제 오류·서버 다운)/Major=게임 진행 불가/Minor=타이포·작은 UI 오류**, Fun QA) → Check(결함 분석·재발 방지 교훈, 회귀 테스트·크로스 플랫폼·런칭 전 베타/사내 테스트, p31~32) → Act(프로세스 재설계·교육, 라이브 후 지속 모니터링·패치 전 QA 반복, p33~34).

### 5-4. Test Case 설계 (p35~49)

- TC 목적: 요구 사항·사양에 따른 기능 검증, 버그 사전 발견, **테스트의 일관성과 재현성 보장** (p35).
- **TC 구성요소 8가지** (p36~38, 예시 p43~46): ① 테스트 케이스 ID ② 테스트 제목 ③ 전제 조건(Pre-conditions) ④ 테스트 데이터 ⑤ 테스트 절차(Steps) ⑥ 예상 결과 ⑦ 실제 결과 ⑧ 테스트 상태(Pass/Fail). 실무 시트에는 카테고리·1차 등급·날짜·재연 방법 컬럼 포함 (p6, p35).
- TC 분류 (p39~40): 기능 테스트 / 유효성 검사(입력값-출력값 일치) / **경계값 분석(최대값·최소값 등 경계조건 중심)** / 성능 테스트.
- 작성 주의사항 (p41): 비즈니스 요구 정확 이해, **가능한 모든 시나리오 커버**, 자동화 가능성 염두, **비정상적 조건 테스트 포함**.
- **좋은 TC 5조건** (p47~48): ① 명확·간결 ② **독립적으로 실행 가능(다른 케이스에 의존 금지)** ③ **단일 시나리오(한 번에 하나의 기능만)** ④ 우선순위(비즈니스 크리티컬 우선) ⑤ **경계값과 예외 처리(정상 입력뿐 아니라 경계값·비정상 입력 고려)**.
- 테스트 보고서 예시 (p49): TC 수/실행/성공/실패/미실행 + 중요도별 결함 수(Critical/Major/Minor).

## 6. 11강 × 장신구 v4 교차 분석

핵심 질문: **v4의 예외 명세 E-01~05·E-201~205는 강의의 QA/TC 기준으로 충분한가?** — 결론부터: 예외 명세는 강의가 요구하는 "경계값·비정상 조건"(p25, p40, p48)의 **씨앗으로서 우수**하나, 강의 기준의 TC는 아니다. TC 구성요소 8가지(전제 조건·테스트 데이터·절차·예상 결과) 형태로 전개되어야 하고, **정상 플로우·확률 통계·회귀** 3개 축이 예외 명세만으로는 커버되지 않는다.
